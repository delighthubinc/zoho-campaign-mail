# Claude 実務指示書（メルマガ制作・配信）

本書は、Claude Chat／Cowork（以下Claude）がセミナー告知メールを単独で制作し、Zoho Campaigns Draft作成まで進めるための実務手順です。運用仕様の正本は [メール生成 正式運用ルール](MAIL_GENERATION_RULES.md) で、本書と矛盾する場合は正式運用ルールを優先します。

本書の手順は、2026-10-19配信の `20261020-akiyazei-4step-20261019`（画像取込 dispatch run 39178427372、PR #57、Draft作成 run 39179069501）で実際に成功した操作だけを標準として記載しています。未検証の操作を標準手順として扱いません。

## 0. 原則

- GitHubの最新mainを技術仕様・デザイン・Validationの正本、Google Driveを案件固有情報・画像素材の正本とする。記憶や過去の会話より正本の現在値を優先する。
- 開催日時、CTA本体URL、UTM、登壇者、配信日、配信回数等は推測しない。情報源同士が食い違う場合は推測で選ばず、ユーザーに確認する。
- 過去campaignは訴求・命名規則の参考にしてよいが、答えをコピーせず、今回の仕様と元素材から導く。
- `main` へ直接pushしない。workflow、script、template、fragment、config、docsを通常campaignで変更しない。
- Test Email、予約送信、本番送信はユーザーだけが行う。Claudeは実行しない。
- 権限・安全確認機能・プロキシで操作が止まった場合は、回避せずにそのまま報告して停止する。

## 1. 実行環境と既知の制約

| 項目 | 状態 |
|---|---|
| リポジトリ接続 | `add_repo`（access: push）で `delighthubinc/zoho-campaign-mail` を接続し、`git clone --depth 1` する |
| GitHub API | REST（`gh api`）は利用可。**GraphQLは利用不可**のため `gh pr list` / `gh pr checks` / `gh issue list` / `gh issue edit` 等は使わず、REST API で代替する |
| Issue / PR本文 | Claude経由で作成・更新したIssue・PRの本文には、通信経路が自動署名（`---` と `_Generated by ..._`）を付加する。PATCHで除去しても再付加される |
| Actionsログ本体 | ダウンロード不可。`gh run view <id> --json jobs` でjob・step単位の結果は取得できる |
| GitHub Pages | シェルからは `*.github.io` へ到達不可。表示確認は内蔵ブラウザ（`Claude_Browser`）で行う |
| Google Drive | Driveコネクタでフォルダ一覧・Sheets・共有設定を読み取れる |
| Zoho Campaigns | Claudeから直接APIを呼ぶ手段はない |

ローカルcloneでは、次の安全策を作業前に設定する。

- `.git/hooks/pre-push` に、`refs/heads/main` 宛てとbranch削除のpushを拒否するフックを置く（ローカルのみ・Git管理外）。
- 作業branchは `git switch -c <branch> --no-track origin/main` で作成し、mainをupstreamにしない。push後は作業branch自身をupstreamにする。

## 2. 制作開始時に確認するもの

GitHub（最新mainをfetchし、commit SHAを控える）:

- `AGENTS.md`、`docs/MAIL_GENERATION_RULES.md`、本書、`docs/preview-qa-checklist.md`
- `templates/base/email.html`、`templates/seminar/blocks/*.html`、`templates/seminar/fragments/*.html`
- `config/email_defaults.json`
- 同一セミナーの既存campaign（前回配信の件名・preheader・訴求・preset・block構成・CTA/UTM・画像）
- 必要に応じて過去の類似campaign（例：前日リマインドの先例）

Google Drive（セミナー素材フォルダ配下の該当セミナーフォルダ）:

- イベント管理シート（開催概要、日時、登壇者、セッション、対象、イベントメモ）
- 集客・クリエイティブフォルダのバナー等の画像（ファイル名、file ID、共有設定）
- 公式LP（管理シートに記載されたURL）を読み、開催情報・申込導線を照合する

申込者・アンケートリスト等の個人情報フォルダは開かない。

## 3. ① 制作条件の一括確認（承認ポイント）

最初の提示で以下をまとめ、最後に「この制作条件で進めてよいですか？」と一度だけ確認する。

- セミナー概要と、情報源間の食い違い（例：開催時間）
- campaign slug（同一セミナーの既存slugとの整合、`<開催日>-<名称>-<配信日>` 等の既存命名に合わせる）
- `zoho_campaign_name`（[命名規則](MAIL_GENERATION_RULES.md#zoho-campaigns管理名称の命名規則) に従う）
- 推奨preset（`standard` / `large`。コード上の描画差はないため、同一セミナー内の一貫性を優先）
- CTA本体URLとUTM（主催企業指定がある場合はその値をそのまま使う。同一セミナーの2通目以降は原則として前回と同じ値）
- 使用するDrive画像のファイル名・file ID・用途
- 推奨block構成、前回配信との違い、主訴求3〜5案、件名の方向性

制作条件の承認をもって、次の画像取込（mainへのActionsによる画像commitを含む）を実行してよい。

## 4. ② 画像取込（workflow_dispatch方式）

Claude経由のIssue本文には自動署名が付き、`[automation:image-import]` workflowが要求する「本文JSONのみ」を満たせない（Issue #56で失敗を確認）。そのため、既存の **Import Drive Images**（`.github/workflows/import-drive-images.yml`）を `workflow_dispatch` で実行する。

実行前の確認:

1. 最新mainの `import-drive-images.yml` を読み、入力が `campaign_slug` と `images_json` であること、commit対象が `campaigns/${CAMPAIGN_SLUG}/images/` のみであることを確認する。
2. 保存先 `campaigns/<slug>/images/` に同名ファイルが存在しないことを確認する（既存ファイルの置換は拒否される）。
3. 同じ入力でローカル検証する。

```bash
python3 scripts/import_drive_images.py \
  --campaign-slug "<slug>" \
  --images-json '[{"drive_file_id":"<DRIVE_FILE_ID>","filename":"<name>.jpg"}]' \
  --manifest "<scratch>/manifest.json"
```

実行（REST API、ref=main）:

```bash
gh api --method POST repos/delighthubinc/zoho-campaign-mail/actions/workflows/import-drive-images.yml/dispatches \
  --input dispatch.json
# dispatch.json: {"ref":"main","inputs":{"campaign_slug":"<slug>","images_json":"[{\"drive_file_id\":\"...\",\"filename\":\"...\"}]"}}
```

成功すると HTTP 204 が返り、ActionsがDriveから取得・検証し、`github-actions[bot]` としてmainへ画像だけをcommitする。

完了確認（すべて満たすまでHTMLプレビューへ進まない）:

1. `gh run list --workflow import-drive-images.yml` / `gh run view <id> --json jobs` で全stepがsuccess。
2. mainの新commitの差分が `campaigns/<slug>/images/` の対象ファイルのみであること。
3. そのcommitの `pages-build-deployment` がsuccess、かつ `github-pages` environmentのdeployment statusが `success`。
4. 内蔵ブラウザで正式URL `https://delighthubinc.github.io/zoho-campaign-mail/campaigns/<slug>/images/<name>` を開き、HTTP 200・画像MIME・画像サイズを確認し、SHA-256がrepository fileと一致すること。画像内の文字情報（日時等）と本文の食い違いもここで確認し、ユーザーに報告する。

失敗時はfail-closedで停止し、失敗stepと原因を報告する。Drive共有設定が原因と考えられる場合はユーザーへ確認を依頼する。

## 5. ③ 訴求決定 → ④ HTML制作・プレビュー前QA

- ユーザーが主訴求を選んだら、追加の細かな承認を挟まず件名・preheader・本文・CTA・HTMLまで作成する。
- HTMLは `scripts/build_email.py` の `render_seminar`（`template_type: seminar`）に原稿JSONを渡して生成し、base・block・fragmentを手で書き換えない。原稿JSONと生成HTMLはリポジトリ外（scratch）に置き、作業ツリーを汚さない。
- block・fragmentに無い表現が必要な場合は、ユーザーの明示指示がある箇所だけcampaign固有に変更する。

プレビュー提示前に `docs/preview-qa-checklist.md` に加えて次を機械的に確認する。

- CTAリンクがすべて制作条件のURL/UTMと一致（同一セミナーの前回と同じ指定なら、前回 `campaign.json` の `cta` と完全一致）
- `<img>` がPages正式URLと共通素材のみで、Drive直リンク・Base64が無い
- ヘッダー・フッター（共通署名）が `email_defaults.json` と一致
- 見出し・本文の重複が無い、未解決placeholderが無い、確定した日時以外の表記が残っていない
- PC幅（1000px）とスマホ幅（375px）で描画し、横スクロール無し・本体640px以内・画像欠け無しを確認する。ローカル描画ではPages URLをリポジトリ内ファイルへ割り当てて確認する

プレビューHTMLとPC/SPキャプチャをユーザーへ送り、修正を受け付ける。ユーザーが「FIX」と明示するまで次へ進まない。

## 6. ⑤ FIX → ⑥ 作業branchへ保存 → ⑦ campaign.json整備・検証

1. FIXされたHTMLのSHA-256を記録する。以後このhashが変わる操作をしない（再生成・整形・改行変換を含む）。
2. 最新mainをfetchし、`git switch -c campaign/<slug> --no-track origin/main` で作業branchを作成する。
3. FIX済みHTMLを `campaigns/<slug>/mail.html` へそのままコピーし、hash一致を確認する。
4. `campaigns/<slug>/campaign.json` を作成する（`campaign_slug`、`zoho_campaign_name`、`template_type`、`preset`、`subject`、`preheader`、`cta`、`content_source: "fixed_html"`、`images`）。subject・preheaderはHTMLの `<title>`・非表示preheaderと完全一致、`images` のURL・altはHTMLと一致させる。
5. 検証を実行する。

```bash
python3 scripts/validate_campaign.py --campaign-slug <slug>
python3 -m unittest discover -s tests
find scripts tests -type f -name '*.py' -print0 | xargs -0 python3 -m py_compile
git diff --cached --check
```

6. commitし、`python3 scripts/check_pr_scope.py --base origin/main --head HEAD` が `eligible=true` と該当slugを返すことを確認する。
7. commit後の `mail.html` hashがFIX時と一致することを確認する。
8. `git push origin HEAD:refs/heads/campaign/<slug>` で作業branchだけへpushし、GitHub上のファイルhashとmainとの比較（2ファイル追加のみ）を確認する。

## 7. ⑧ PR作成（承認ポイント）

PR作成はユーザーのHTML FIXとPR作成許可を確認してから行う（FIX時にあわせて許可を得てよい）。

1. 最新mainとの比較で、behind 0・差分が `mail.html` と `campaign.json` の2ファイルのみであることを再確認する。
2. REST APIで作成する。

```bash
gh api --method POST repos/delighthubinc/zoho-campaign-mail/pulls --input pr.json
# pr.json: {"title":"...","head":"campaign/<slug>","base":"main","body":"...","draft":false}
```

3. PRを再取得し、`base.ref == "main"`、`head.ref` が作業branch、`head.repo` が同一リポジトリ、変更ファイル2件であることを確認する。
4. PR作成後にbaseを変更しない。Claudeはauto-mergeの有効化・手動mergeを行わない。

## 8. ⑨ Validation → auto-merge → Pages → Zoho Draftの確認

既存Actionsが自動実行する。Claudeは結果を読み取って報告する。

| 確認対象 | 方法 | 成功条件 |
|---|---|---|
| PR Validation | `gh api repos/.../commits/<head_sha>/check-runs` | `validate-campaign` がsuccess |
| auto-merge | 同上、`gh api repos/.../pulls/<n>` | `enable-auto-merge` が `validate-campaign` 完了後にsuccess、PRが `zoho-campaign-mail-automation[bot]` によりmerge |
| merge内容 | merge commitの差分と `mail.html` hash | 2ファイルのみ、hashがFIX時と一致 |
| Pages | `gh run list --commit <merge_sha>`、内蔵ブラウザ | `pages-build-deployment` success、公開HTMLのhash・件名・画像・CTAが一致 |
| Zoho Draft | `gh run view <id> --json jobs` | `Verify Pages and Create Zoho Draft` の全stepがsuccess（Create Zoho Campaigns Draft を含む） |
| 冪等性ledger | `[automation] Zoho Draft ledger` Issueの最新コメント | 該当slug・merge commit・`state:created` |

Validation失敗、auto-merge未実行、Pages未完了、Draft作成失敗のいずれかでは、そこで停止して失敗箇所を報告する。再実行やworkflowの手動起動は、ユーザーの許可なく行わない。

### Zoho Campaigns管理画面URLの報告

Draft作成が成功したら、最終報告に該当キャンペーンの管理画面へ直接開けるURLを記載する。URLは実際の画面またはAPI応答から取得したものに限り、推測で組み立てない。

現状、`create_zoho_draft.py` は作成成功の判定だけを行い、キャンペーンIDを出力・保存していない。また内蔵ブラウザがZoho Campaignsにサインインしていない場合、Claudeは管理画面を開けない（パスワード入力は行わない）。URLを取得できない場合は、その理由と必要な対応（ユーザーによる内蔵ブラウザでのサインイン等）を報告する。

## 9. ⑩ ユーザーの手動操作

最終報告で、Zoho Campaigns上の該当Draft（`zoho_campaign_name`）を示し、ユーザーにDraft確認 → Test Email → PC/スマホ表示確認 → CTA確認 → 予約または本番送信を依頼する。Claudeはこれらを実行しない。

## 10. 承認ポイントと停止条件の一覧

| タイミング | 必要なユーザー判断 |
|---|---|
| ① 制作条件提示後 | 制作条件の承認（画像取込の実行を含む） |
| ③ 訴求案提示後 | 主訴求の選択 |
| ④ プレビュー提示後 | 修正指示または「FIX」 |
| ⑧ PR作成前 | PR作成の許可（FIX時の許可でも可） |
| ⑩ | Test Email・本番送信はユーザーのみ |

次の場合は停止して報告する。

- 情報源の食い違い、CTA/UTM・日時・回数など重要情報の不明
- 画像取込失敗、Pages正式URL未確認
- FIX後の `mail.html` hash不一致、許可範囲外のファイル変更
- `check_pr_scope.py` が通常campaignで `eligible=false` を返す
- Validation失敗、auto-merge未実行、Pages・Draft作成の失敗
- 権限・安全確認機能・プロキシによる操作拒否
